# Periodic EnvHead ML/MM-EM and ML/MM-MM

From the `mace-ena` directory:

```bash
python -m mace.modules.envhead.script.mlmm --initial
# Edit md.json for your model and molecular system.
python -m mace.modules.envhead.script.mlmm --config md.json
```

`--initial` writes a generic `md.json` in the current directory, without starting
MD or overwriting an existing file. Set `model`, `pdb` and `ml_indices` before
running. The first two start as `null`; `ml_indices` starts as an empty list and
must contain the zero-based OpenMM indices of one complete molecule. Set its
`total_charge` explicitly for a charged molecule. Defaults contain no trained
Amino model path, peptide geometry or hardcoded atom selection. The template
and missing optional controls use the same Python defaults, independent of any
example JSON beside the source code.

Paths resolve relative to the user's JSON file. Set `solvated` to select input
preparation:

- `false` (default): supply a solute-only PDB. Add water, optionally neutralize
  and add NaCl, then parameterize and minimize. Original solute atom indices
  are retained; water and ions are appended.
- `true`: supply an already solvated PDB with a periodic `CRYST1` record.
  Preserve its atoms, coordinates, ions and box, parameterize with `forcefield`,
  and proceed directly to minimization. No water or ions are added, and no box
  is rebuilt. `system_xml` is optional.

The existing `minimize` flag still controls minimization, and `nvt_ps`/`npt_ps`
still control subsequent equilibration in both cases. Supply a complete,
appropriately protonated PDB; this driver does not add missing hydrogens.

For a new water box, for example:

```json
{
  "forcefield": ["amber19/protein.ff19SB.xml", "amber19/spce.xml"],
  "solvated": false,
  "water_model": "spce",
  "padding_nm": 1.2,
  "box_nm": null,
  "neutralize": true,
  "ionic_strength_molar": 0.15
}
```

These are preparation fields to edit in the full `md.json` generated by
`--initial`; the example is not a complete run configuration.

| Field | Meaning and default |
|---|---|
| `forcefield` | OpenMM XML files; default ff19SB plus `amber19/spce.xml`, including matching ions |
| `water_model` | Initial water-box template passed to OpenMM `addSolvent`; default `spce` |
| `padding_nm` | OpenMM solvent padding in nm; default 1.2 |
| `box_nm` | Optional explicit `[Lx, Ly, Lz]` in nm; default `null`, using padding instead |
| `neutralize` | Add counterions during fresh solvation; default `true` |
| `ionic_strength_molar` | Added NaCl salt concentration in mol/L; default 0, with 0.15 giving 150 mM |

Padding automatically determines a cubic box from the solute size, so its
dimensions need not be specified. It follows OpenMM's bounding-sphere
definition: cube width is `max(solute_sphere_diameter + padding, 2*padding)`.
This controls the spacing between solute periodic copies; it does not mean
adding that distance to each face of an axis-aligned molecular bounding box.
An explicit `box_nm` takes precedence over padding for fresh solvation.
`solvated: true` ignores these solvation settings and retains the PDB box.
The current periodic runtime requires an orthorhombic box; automatic cubic
solvation satisfies that requirement.

The final water charges, LJ and constraints come from **`forcefield`**.
`water_model` selects the initial solvent packing template. For example,
TIP3P uses `amber19/tip3p.xml` with `water_model: "tip3p"`; OPC3 uses
`amber19/opc3.xml` with the compatible three-site `water_model: "tip3p"`
template, followed by constraint application/minimization. OpenMM does not
accept `opc3` as an `addSolvent` template name. SPC/E is a default reflecting
the training data, with no restriction on loading other supported water
parameters. The current ML/MM runtime rejects virtual sites, so four-site OPC
is outside its supported scope. See the
[OpenMM solvation guide](https://docs.openmm.org/latest/userguide/application/03_model_building_editing.html#adding-solvent).

NaCl pairs replace water molecules during fresh solvation. The requested salt
concentration excludes the counterions added for neutralization; finite boxes
contain an integer number of pairs. With `solvated: true`, existing ion counts
are kept even if `ionic_strength_molar` is nonzero. For AMBER water and ions,
use the matching `amber19/<water>.xml` file.

Supply both `system_xml` and `pdb` to reuse an existing native PME System and
matching coordinates. This route takes precedence over `solvated`, preserves
the serialized parameters and box, and performs no solvation, neutralization
or force-field reparameterization. A hydrated PDB alone can instead be
parameterized directly with `solvated: true`. MM water is rigid, and
constraints within the ML molecule are removed by default. Set
`keep_ml_constraints: true` to retain its native input constraints, for example
when using X--H constraints with a 2 fs timestep. This retains constraints from
the supplied System; it does not add constraints to an unconstrained input.

## Embedding mode

Both modes load the **same trained ENA checkpoint**, retaining its fine-tuned
MACE parameters and total-charge conditioning:

| `mode` | ML internal energy | ML--MM electrostatics |
|---|---|---|
| `mlmm-em` (default) | ENV-conditioned MACE | Predicted environment-conditioned charges |
| `mlmm-mm` | Vacuum MACE, without ENV input | Fixed ML and MM charges from the original OpenMM force field |

Set `"mode": "mlmm-mm"` in the JSON, or override it on the command line:

```bash
python -m mace.modules.envhead.script.mlmm --config /path/mm.json --mode mlmm-mm
python -m mace.modules.envhead.script.mlmm --config /path/em.json --mode mlmm-em
```

MM mode replaces the ML molecule's **entire internal classical energy** with
the trained vacuum ML energy. Original ML--MM LJ and fixed-charge periodic
Coulomb interactions, plus MM internal forces, remain. ML and MM atoms both
receive the derivatives of these interactions. Fixed ML charges are read from
the original `NonbondedForce`; their sum must match `total_charge`.
The callback's `charges` output is
this fixed force-field charge array in MM mode.

MM mode evaluates one QM backbone with total-charge conditioning. It skips
ENV neighbor encoding, ENV feedback, field projections, feature mixers and
the learned charge head. Native OpenMM PME handles all fixed charges. The
PythonForce receives only ML coordinates and returns their vacuum ML forces
plus an isolated intramolecular Coulomb subtraction, avoiding a second PME
calculation and full-system host transfers. The loaded model's weights
and ordinary inference/training behavior are unchanged. This interface
expects an EnvHead checkpoint, including in MM mode; it does not substitute the
original, unfine-tuned OFF23 model.

The neural network uses the configured dtype (`float32` by default). EM Torch
PME follows that dtype; native MM PME uses the OpenMM platform precision
(`mixed` in the supplied CUDA configuration). Some scalar electrostatic terms and the final
energy sum use float64, as in the existing EM callback. The validation utility
separately loads the same weights in float64 on CPU for finite differences;
that reference calculation is excluded from production timings. Increasing
evaluation precision does not recover additional training precision.

Use separate output directories for EM and MM. Existing JSON files without
`mode` retain EM behavior. Switching
mode changes the physical Hamiltonian and requires a new run, including new
PLUMED history; same-mode production extension remains supported.
Earlier experimental MM checkpoints using Torch PME have a different System
layout and require a fresh run with the current callback.
Only the production EM and native-PME MM callbacks remain; the former
Torch-PME MM comparison implementation has been removed. The validation CLI
uses the same callback selected by the MD driver. MM callback diagnostics
cover ML coordinates; full-system OpenMM timings and MD include both regions.

The defaults are 0.5 fs, 300 K, 1 bar, friction 1 ps⁻¹, seed 114514 and volume
moves every 25 steps. A 1 nm nonbonded cutoff, 0.9 nm LJ switch and PME tolerance
10⁻⁴ apply to the new box. The run minimizes, equilibrates for 10 ps NVT and
20 ps NPT, then runs 100 ps of the selected production `ensemble`:

| `ensemble` | Integrator | Production controls |
|---|---|---|
| `nve` | Verlet | Fixed box, no thermostat or volume moves |
| `nvt` | LangevinMiddle | Fixed box at `temperature_k` |
| `npt` | LangevinMiddle + MonteCarloBarostat | `temperature_k`, `pressure_bar` |

Set `nvt_ps` or `npt_ps` to zero to omit that equilibration stage. Durations must
be integer multiples of `timestep_fs`. A Context is reused while the ensemble
is unchanged. Ensemble transitions transfer positions, velocities, box, time,
parameters and step count to a new Context after releasing the previous one.
The same loaded Torch model and callback serve every stage. These usage
controls stay outside `EnvHeadConfig`. Initial thermal velocities are projected
onto the retained constraints and have their mass-weighted center-of-mass
velocity removed before integration. The first CMMotionRemover application
therefore avoids an artificial net-translation energy drop in NVE diagnostics.

Outputs include `initial.pdb`, `classical_input.xml`, `minimized.pdb`, stage
`nvt`/`npt` logs and DCD files, production `md.log`/`md.dcd`, `checkpoint.chk`,
`final.pdb`, `final_state.xml` and
`effective_config.json`. Production logs report the shifted potential energy
described below. A fresh run refuses an output directory containing an initial
structure or checkpoint.

```bash
python -m mace.modules.envhead.script.mlmm \
  --config md.json --resume /absolute/path/to/output/checkpoint.chk
```

Restart loads the saved original classical system and initial topology,
rebuilds the same callback/System/integrator, then loads the binary checkpoint.
It skips solvation, minimization and equilibration and preserves the checkpoint
clock, velocities, step count and RNG state. `production_ps` is the **total
production target**: increasing it extends a completed run. In the same output
directory, production DCD and log files append when their timing is continuous
with the checkpoint and the reporting interval is unchanged. DCD headers store
the actual global first reporting step. The driver inspects frame count, first
step, interval, final step, complete-frame size and the last log step before
appending. Changing cadence, outputs beyond the checkpoint, missing frames or
damaged output starts `md_resume_<checkpointstep>.dcd` and `.log`, preserving
earlier files. Subsequent clean resumes append to that active segment. A
nonempty segment of the same name is preserved and requires a different output
directory. A different destination is checked before any input or configuration
write: nonempty run files that would be replaced cause rejection. New or empty
directories and unrelated files remain usable. When a short run created no
output frames, empty DCD/log files are
opened fresh so the first subsequent frame receives a valid header. The latest
trajectory segment is identified from its filename and DCD/log timing.
The native checkpoint supplies the current step/time; the saved
`effective_config.json` supplies the original equilibration durations used to
compute the completed production length. Resume retains those durations even
if the new input clears `nvt_ps` or `npt_ps`. Resume does not fingerprint
models, source files, configuration or PLUMED input. Keep the same physical setup
when extending a trajectory; EM/MM mode or timestep changes require a new run.
Keep `checkpoint.chk`, `effective_config.json`, `classical_input.xml` and
`initial.pdb` together. No checkpoint JSON sidecar is generated or read. Binary
checkpoints also require compatible OpenMM version, platform and hardware;
`final_state.xml` is a portable state export, with a different RNG contract.

## Optional PLUMED bias

Provide a PLUMED input file through the CLI or the `plumed` JSON field (default
`null`). The CLI overrides JSON; CLI paths are relative to the working directory,
while JSON paths are relative to the JSON file. In the existing ML/MM environment:

```bash
python -m mace.modules.envhead.script.mlmm \
  --config md.json --plumed /path/to/plumed.dat
```

Prepare this PLUMED input for your own topology and chosen CVs; the source
directory contains no molecule-specific DAT template. PLUMED uses **one-based atom indices**,
nm, ps, kJ/mol and radians by default. Its `TEMP` must match the intended ensemble.
The runner passes the script to the official `openmmplumed.PlumedForce`; CV and
bias algorithm settings stay in that file. MetaD, OPES and other actions use the
same loading path, subject to the modules enabled in the linked PLUMED library.
Geometric CVs do not require another EnvHead forward. Charge-based CVs do not
automatically receive the neural charges from this interface.

Minimization and equilibration remain unbiased. At production start the driver
releases the old Context and attaches the bias before creating the production
Context, even when the ensemble is unchanged. Coordinates, velocities, box,
global time and step count transfer normally. NPT volume acceptance includes
the bias energy through OpenMM's ordinary Force interface.

PLUMED runs inside **`output/plumed/`**, containing `input.dat` and all relative
PLUMED outputs, such as `HILLS` and `COLVAR`. Use relative output/history paths
inside this working directory; use absolute paths for external reference
PDBs or included input files. Concurrent simulations need separate processes
and output directories. The runner appends `FLUSH STRIDE=1` to flush history
at updates, including a final partial checkpoint interval. This affects I/O
only. The production `md.log` potential/total energy includes the bias; print
the bias in `COLVAR` when analyzing or reweighting it. Unbiased histograms need
the reweighting appropriate to the chosen method.

Biased runs write the same native `checkpoint.chk`. Before saving it, the
driver evaluates/flushes the current bias step, then uses OpenMM's checkpoint
writer. PLUMED history stays in `plumed/`; no periodic ZIP or directory snapshot
is created. Resume loads the native checkpoint and sets the plugin's
[restart flag](https://www.plumed.org/doc-v2.9/user-doc/html/_r_e_s_t_a_r_t.html):

```bash
python -m mace.modules.envhead.script.mlmm \
  --config md.json --plumed plumed.dat --resume result/checkpoint.chk
```

Keep `plumed/` alongside the ordinary restart files. Same-directory resumes
use it in place; a different output destination copies it once at startup.
On resume, recognized PLUMED text files with a `time` column are checked against
the loaded checkpoint clock. Incomplete lines or newer history cause an error;
the runner does not truncate history or synthesize missing bias state. After
an interruption, restore histories/action state matching the checkpoint before
continuing. Files without a PLUMED time-column header and native `bck.*` backups
are skipped. These checks do not validate arbitrary binary or
untimed action state.
Each action must write its own restart state: for example, configure OPES
`STATE_WFILE`, `STATE_RFILE` and a `STATE_WSTRIDE` aligned with checkpoint times.
The driver does not reconstruct action state that PLUMED has never written. An existing
unbiased binary checkpoint cannot be turned into a biased restart by changing
the input; starting enhanced sampling from an unbiased endpoint is a new run.

Install the optional plugin against the **same OpenMM** used by ML/MM:

```bash
conda install -c conda-forge openmm-plumed
```

Inspect the solver's package changes before using Conda in an existing Torch
environment. For a custom OpenMM installation, the official plugin can instead
be built with `OPENMM_DIR`, `PLUMED_INCLUDE_DIR` and `PLUMED_LIBRARY_DIR` pointing
to the installed headers/libraries. No `plumed` Python binding is required.
Without a `plumed` input, the plugin is not imported and unbiased checkpoints
use the native OpenMM restart path.

## Energy and force ownership

With one complete ML molecule A and a fixed-charge MM environment B, EM uses

\[
E = E_{BB}^{\mathrm{MM,PME}} + E_{AB}^{\mathrm{LJ}}
  + E_A^{\mathrm{EnvHead}}(R_A;V_B,\mathbf E_B)
  + \Delta E_{AA}^{\mathrm{image}}(q).
\]

MM mode uses

\[
E = E_{BB}^{\mathrm{MM,PME}} + E_{AB}^{\mathrm{LJ}}
  + E_A^{\mathrm{vac},\theta}(R_A)
  + \sum_i q_i^{\mathrm{FF}} V_{B,i}
  + \Delta E_{AA}^{\mathrm{image}}(q^{\mathrm{FF}}).
\]

Here the fixed charges and LJ parameters come from the supplied classical
system (AMBER for the example). The cross term has no factor 1/2. In MM the
equivalent execution ledger is native full fixed-charge Coulomb plus vacuum ML
energy minus isolated ML point-charge Coulomb. ML exception products in the
native NonbondedForce are restored to the full particle charge products before
this subtraction, so no AMBER 1-4 electrostatic scaling remains in the ML
internal energy. Periodic ML images, self and plasma terms remain in native
PME. Its mesh implementation differs from Torch PME in EM; compare converged
energy/forces rather than expecting bitwise identity between these backends.

The native OpenMM NonbondedForce keeps BB PME, BB LJ and BB exceptions.
In EM, ML charges and intra-ML exception charge products are cleared there.
In MM, ML particle charges are retained and ML exception products are restored
to full particle products. ML LJ well depths and intra-ML exception LJ well
depths are cleared in both modes. All ML bonded energies are removed. ML
constraints are removed unless `keep_ml_constraints` is enabled.
Zero-energy harmonic bonds preserve the ML molecular
connectivity required for molecular volume scaling. A native
CustomNonbondedForce interaction group adds AB LJ from the original
Lorentz–Berthelot sigma/epsilon parameters, cutoff and switch. Its exclusions
match the native force, permitting shared GPU neighbor lists. Native
dispersion correction and custom AB long-range correction use their own
OpenMM finite-size conventions; their finite-system tail need not equal a
full-minus-isolated native-tail subtraction exactly.

EnvHead receives minimum-image near chemical environments plus the full
periodic MM potential and field. Its explicit electrostatic contribution is
\(\sum_i q_i V_{B,i}\). The image term is point-charge periodic AA Coulomb
energy minus isolated AA Coulomb energy, including Ewald self and uniform
neutralizing-background terms. The convention is conducting boundaries with
the reciprocal zero mode removed; the same potential convention is used in
the descriptor and explicit energy. No adjustable potential gauge is exposed.
The mesh shape and Ewald splitting are fixed from the initial box; interpolation
and volume factors are recomputed for every current or trial NPT box.

In EM the callback differentiates this **complete scalar energy** through geometry,
the periodic fields and the model's field-dependent charges. Both ML and MM
atoms receive its derivatives. Charges are produced in one model evaluation;
this point-charge image correction uses those predicted charges without an
SCF loop. It is a charge-based approximation to periodic electronic images.
In MM the callback differentiates vacuum ML energy minus isolated internal
point-charge Coulomb; native OpenMM supplies all periodic fixed-charge Coulomb
forces. No learned charge-response derivatives are evaluated. Both modes retain
complete coordinate derivatives.
Short-range learned interactions with replicas of the same ML molecule are
outside the interface; EM rejects a detected self-image contact.

For fixed ML composition, the common model reference energy \(E_0\) is a
constant. The callback omits it **before** float32 total-energy assembly and
accumulates the variable energy in float64. Forces and energy differences
retain their meaning while NVE logs avoid loss of small differences under a
large constant offset. The reported potential-energy zero therefore differs
from the raw model's absolute energy zero.

## Optional dependencies and offline setup

The existing MACE/Torch/PyG/cuEq environment is retained. Optional dependencies
are OpenMM 8.6.1 with PythonForce and torch-pme 0.5.0. CUDA OpenMM additionally
needs the **separate** OpenMM-CUDA-12 8.6.1 plugin and its NVRTC dependency; the
base OpenMM wheel supplies Reference/CPU/OpenCL. `requirements.txt` records the
CUDA option. `offline.sh` is an optional deployment helper, separate from MD.
Download matching wheels on an online machine, copy that directory to the
offline server, then install locally with `pip --no-index --find-links`.
No download or network access is needed during the offline installation;
the complete compatible wheel directory must already have been transferred.

```bash
# Offline H20 server: export installed Torch CUDA requirements, without network.
PYTHON=/server/env/bin/python bash mace/modules/envhead/script/mlmm/offline.sh \
  constraints > torch-cu126-constraints.txt

# Copy that small text file to the online office machine, then download wheels.
# Office Torch may use a different CUDA version; the exported server file controls
# this download. Both machines use Linux x86_64 and CPython 3.10 for this recipe.
PYTHON=/office/env/bin/python bash mace/modules/envhead/script/mlmm/offline.sh \
  download /path/to/mlmm-wheels cuda12 /path/to/torch-cu126-constraints.txt

# Transfer the wheel directory, then run in the existing offline environment:
PYTHON=/path/to/python bash mace/modules/envhead/script/mlmm/offline.sh \
  install /path/to/mlmm-wheels cuda12
```

The `constraints` command reads package metadata and prints the target Torch
package's exact NVIDIA requirements. It also limits an OpenMM-only NVCC
dependency to the declared CUDA runtime's major/minor version when Torch has
no NVCC requirement. Exporting on a Torch 2.11/cu126 server and passing that
file as the fourth download argument works from an office Torch 2.8/cu128
environment. The three-argument download command remains available when the
online machine already has the target Torch stack; it derives local constraints.

The CUDA plugin dependency closure uses the selected constraints file. This
keeps NVRTC and the optional NVCC compiler aligned with the server's CUDA
version. Before installing any wheel, the script checks the saved constraints
against active Torch metadata and the derived NVCC bound. Installation
uses `--no-index --find-links`; Torch, PyG and Triton are never installation
targets. Their versions are checked before and after. The final dependency
check loads NVRTC, lists OpenMM platforms and checks Torch CUDA availability.
The NVIDIA driver must support the installed toolkit's generated PTX. A CUDA
failure is reported directly. There is no automatic platform fallback.

Use backend `cpu` for a wheelhouse containing only the base optional packages,
and set `device: "cpu"`, `platform: "Reference"` or `"CPU"`,
`platform_properties: {}`, and `enable_cueq: false` in the usage config.
For CUDA, dtype defaults to float32, native OpenMM precision to mixed, and the
existing EnvHead cuEq conversion runs before parameters are frozen.

PythonForce transfers positions and forces through the host on each call.
It receives the explicit ordered list of all particles, which uses OpenMM's
particle-copy kernel and avoids a CUDA PME stall observed with the implicit
whole-system coordinate path in OpenMM 8.6.1. All particles and forces retain
their original topology order. In CUDA mixed precision this copy uses the
native float32 position buffer, matching the default float32 model input.
The callback temporarily selects Torch's primary CUDA context and restores
OpenMM's caller context afterward, including when evaluation raises.
CUDA EM searches QM--ENV neighbors on the GPU in double precision for discrete
membership, then reconstructs edge vectors from the original model-dtype
coordinates. One current-frame cross-neighbor search covers both real-space
PME and the near-field graph; each consumer filters its own physical cutoff.
QQ and ENV--ENV retain cKDTree searches, keeping large ENV--ENV sets sparse.
No topology is reused across MD steps, and no additional neighbor dependency
or user tuning option is required. CPU evaluation retains cKDTree.

For a fixed box, dtype, device and mesh, the callback reuses torch-pme's Coulomb
kernel, mesh dimensions, spectral convolution and integer stencil. The
fifth-order P3M weights, charge spreading and potential gathering use scripted
tensor functions with flat mesh indices. Combined stencil weights are computed
once per query/source and reused within that frame; coordinate-dependent
indices and weights remain frame-local. A box change
creates a new convolution without mutating objects retained by earlier frames;
rejected NPT trials therefore cannot overwrite an old frame's force graph.
Cells requiring gradients use a fresh spectral graph every call. The B-spline
polynomials match torch-pme's P3M interpolation; its FFT convolution and Coulomb
kernel remain in use. Field autograd and final two-sided energy derivatives
retain the complete coordinate graph. Caches belong to the
runtime callback, outside model parameters and checkpoint state. Existing EM
checkpoint layout and native-PME MM behavior are unchanged.

Host transfers and PythonForce callback costs remain. Runtime claims require
measured public-path timings; neighbor-only speedups do not describe a full MD
step. Run the periodic-runtime unit tests together with the existing ML/MM
bridge, restart, PLUMED and background-force tests when modifying this path.

## Scope and validation

The development validator lives under `tests/extensions/envhead/`. From the
repository root, run real-model numerical checks and short MD timings with the
same config:

```bash
python -m tests.extensions.envhead.validate_mlmm \
  --config md.json \
  --output /path/to/mlmm-validation.json --steps 100
```

This reports coordinate finite differences in float64, float32 versus float64,
rewrapping and trial-box restoration, 100-step NVE/NVT/NPT smoke runs, and
end-to-end callback/OpenMM E/F timings (5 warmups, 20 repetitions, median/IQR).
The classical baseline contains the retained BB/AB terms. The short runs do
not replace equilibration or establish thermodynamic convergence. Local source
acceptance results are recorded separately under `output/mlmm/`.

The reciprocal implementation uses torch-pme's fifth-order smooth cardinal
B-spline assignment and its potential-mode influence correction (the library
calls these building blocks `P3M`). This approximates the same conducting
point-charge Ewald energy. B-splines avoid the stencil jumps of Lagrange
interpolation, which matter when the network also consumes the field and its
coordinate derivatives. Mesh dimensions stay fixed across NPT trial volumes.

The initial interface requires one complete connected ML molecule, a positive
orthorhombic periodic box, one native PME NonbondedForce, and an EnvHead
`once`/`all` model. It rejects virtual sites, ML/MM covalent terms or constraints,
cross-region nonbonded exceptions, parameter offsets and unsupported forces.
The box must remain larger than twice the relevant electrostatic and model
local cutoffs throughout NPT.

Targeted tests check classical energy/force ownership, CMAP and constraint
handling, BB/AB force separation, periodic geometry, two-sided scalar force
derivatives, NPT trial-box restoration, short MD, ensemble transitions and
production restart. These establish implementation behavior on controlled
fixtures. Scientific acceptance separately requires relevant QM/point-charge
references, strong-field transfer checks, convergence with timestep/PME
accuracy and box size, NVE energy drift, and NVT/NPT structural and density
checks using the selected trained model. The default production length is a
usage example and is not a claim of physical validation.

[OpenMM custom nonbonded interactions](https://docs.openmm.org/latest/api-python/generated/openmm.openmm.CustomNonbondedForce.html),
[OpenMM solvation](https://docs.openmm.org/latest/api-python/generated/openmm.app.modeller.Modeller.html),
and [torch-pme](https://github.com/lab-cosmo/torch-pme).
